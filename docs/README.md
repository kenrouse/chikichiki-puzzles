# Documentation

このディレクトリには、READMEだけでは説明しきれない設計判断と、将来の検討事項を置きます。

## 文書一覧

- [Design decisions](./design-decisions.md): 現行実装が守る設計契約、旧作との関係、検証・公開方針をまとめたliving document。
- [Roadmap](./roadmap.md): 検討済みだが未実装の要件と発展案。実装を確約するものではありません。
- アプリ内の「ゲーム制作ノート」: 利用者向けの生成アルゴリズム解説。実装は`src/pages/20260811_GuidePage.tsx`です。
- アプリ内の「遊び方」: 利用者向けのルールと攻略手順。実装は`src/components/20260812_GameHowTo.tsx`です。

## 文書の置き方

### リポジトリへ残すもの

- 利用者や開発者が繰り返し参照する情報。
- 現行実装の理由、守るべき契約、検証方法。
- 採用済みの重要な判断と、その判断を変える条件。
- 複数のIssueや変更にまたがる中長期の方向性。

### そのままコミットしないもの

- 調査途中の断片、個人的なTODO、貼り付けただけのログ。
- すぐに不要になる作業メモや、結論が確認されていない仮説。
- パスワード、トークン、個人情報、非公開データ。

短期メモはローカルの一時領域またはGitHub Issuesに置き、再利用価値が確認できた内容だけを整理して`docs/`へ昇格します。完了条件や担当・期限を追跡する作業項目は、Markdown文書ではなくGitHub Issuesを正本にします。

## 命名規則

- 長期更新する文書は、日付を付けずにlowercase kebab-caseの英語名を使います。例: `design-decisions.md`、`testing-guide.md`。
- 日付はファイル名ではなくGit履歴で追跡します。文書を更新するたびに別ファイルを増やしません。
- 会議録や時点スナップショットのように日付自体が識別子になる文書だけ、`YYYYMMDD-topic.md`を使います。
- 重要な判断を変更不能な個別記録として残す必要が生じた場合は、`docs/adr/0001-short-title.md`形式のArchitecture Decision Recordを追加します。
- ルートの`README.md`はプロジェクトの入口として残し、詳細は`docs/README.md`からたどれるようにします。

## 更新ルール

- 実装と同じコミットで関連文書を更新します。
- 相対リンクを使い、移動時は参照元を検索して更新します。
- 現行仕様と将来案を混在させず、未実装項目は`roadmap.md`へ置きます。
- 古い内容を追記で打ち消さず、living documentの本文を現在の正しい状態へ更新します。過去の内容はGit履歴で確認します。
