# ちきちきパズルズ ゲーム設計・実装判断

> Status: Living document. 現行実装が守る判断を記載し、未実装候補は[Roadmap](./roadmap.md)へ分離する。

## この文書の目的

本書は、2006年から2011年の旧作を2026年のWebアプリとして再構築した際の判断を、今後の修正で失わないための記録である。機能一覧ではなく、ゲームとして守る契約、旧版との関係、検証方法、再発しやすい問題を正本として残す。

## 旧作の位置付け

- `iapp_numberplacei` と `AutomaticSudoku` は、完成盤を作って数字を抜く数独だった。LEVEL1からLEVEL3は、抜いたマスを候補計算で絞れるか判断する手筋の段階であり、LEVEL4とLEVEL5はメニューだけで未実装だった。
- `shiseni` は別用途のツールではなく、2009年に作った「四川省ｉ」のiアプリだった。現在の四川省は、その牌合わせと2回以内に曲がる経路規則を再構築したものになる。
- 現行版は旧コードの直接移植ではない。当時のゲーム性と見覚えのある名前を出発点にし、純TypeScriptのエンジン、一意性・可解性の検査、seed再現、アクセシビリティ、PWAを追加した新実装である。
- 旧版と同じ発想を継承した箇所と、2026年版で追加した保証を説明上も分ける。「従来アルゴリズムのまま」とは表現しない。

## 全ゲーム共通の設計契約

### ルールとUIを分離する

盤面生成、経路探索、勝敗判定などはReactに依存しない純TypeScriptへ置く。UIはエンジンの状態を表示し、マウス、タッチ、ペン、キーボードの操作を同じ状態遷移へ接続する。これにより、ルールをDOMなしでテストし、表示変更でゲームの公平性を壊さない。

### 同じseedから同じゲームを再現する

ゲーム生成に`Math.random()`を直接使わず、seed付きの決定的乱数を使う。共有URLには盤面を再現するために必要な追加条件も含める。数独と四川省はseedと難易度、マインスイーパはseed、難易度、最初のマス、推測不要モードを共有契約とする。

seedの意味を変える変更は既存URLとの互換性を壊す。生成順序や乱数呼び出し回数を変更する場合は、その影響を意識し、必要ならURLまたは保存データへ生成バージョンを追加する。

### 公平性を生成時に検証する

「たぶん解ける」盤面を表示後に補正せず、候補盤面を生成してからソルバーで契約を検証し、合格した盤面だけを採用する。検証不能な難易度名や、手掛かり数だけを難しさの根拠にしない。

### ローカル優先で中断に耐える

進行、設定、記録は`localStorage`へ保存し、アカウントや常時通信を要求しない。共有操作以外でプレイ情報を外部へ送らない。保存スキーマを変えるときはキーの版を上げるか、旧データからの移行を用意する。

### 遊び方と多言語

- 各ゲームの難易度操作と盤面の間に、初見利用者向けの短い遊び方を表示する。目的と3つの基本ルールは常時読め、詳細な操作とクリア条件は展開式にする。
- 説明は非表示にできるが、同じ場所に「遊び方」再表示ボタンを残す。表示状態は`chikichiki:how-to:v1`へゲーム別に保存する。
- 表示言語は日本語と英語に対応し、ヘッダーと設定画面の両方から即時切替できる。可視テキストだけでなく、ツールチップ、盤面の`aria-label`、共有・確認・結果ダイアログ、制作ノートも同じ言語へ揃える。
- 言語を追加した設定は`chikichiki:preferences:v7`へ保存し、既存の`v6`設定を既定値へマージして移行する。言語変更でテーマ、音量、ペン設定を失わない。
- `html[lang]`とブラウザータイトルも現在言語へ追従させる。ゲーム状態、seed、共有URLは言語から独立させ、言語切替で盤面を作り直さない。

### ランクと次の目標

- 数独: `クリア秒数 + ヒント × 90 + ミス × 35`。Sは299以下、Aは300〜599、Bは600〜999、Cは1,000以上。
- マインスイーパ: `スコア / (安全マス数 × 10)`。Sは3.8以上、Aは2.7以上、Bは1.7以上、Cは1.7未満。時間はランクに含めず、ベストタイムとして別管理する。
- 四川省: `クリア秒数 + シャッフル × 120`。Sは359以下、Aは360〜719、Bは720〜1,199、Cは1,200以上。ヒントはランクに含めない。
- ランク計算は`src/games/20260812_ranking.ts`の純関数を正本とし、遊び方と結果画面で同じ閾値を使う。
- 結果画面には次ランクの上限／下限、現在値から必要な改善量、同じペナルティ行動なら目標クリア時間を表示する。S達成時とゲームオーバー時は専用メッセージにする。

### TOPと遊び方のレイアウト

- TOP画面はビューポート高を二重に確保しない。`main`のflex領域に通常フローで配置し、1365 × 768以上ではアプリフッター下端がビューポート内に収まることを確認する。
- 遊び方帯はデスクトップ28px、狭幅16px以上の左右余白を持つ。背景帯は全幅のまま、本文・詳細・ランク表が端へ張り付かないようにする。

## 数独

### 3つの問題タイプ

- `classic`: 完成盤から1セルずつ抜き、Algorithm X / Dancing Linksで一意解を維持する。
- `symmetric`: 180度回転で対応するセルを組として抜く。残ったどの対応ペアもさらに抜くと一意解を失う、ペア最小問題とする。
- `killer`: 一意解classic盤面の与え数字を保持し、残りの空欄だけを連結ケージへ分割する。ケージ内は数字の重複を禁止し、合計値を満たす。与え数字とケージ制約の組み合わせで一意解を構成する。

問題タイプはseedとともに共有URLへ保存する。variant指定がない既存URLと保存データは`classic`として扱う。

### 人間向け手筋評価

裸／隠れシングル、ロック候補、裸／隠れペア、X-Wing、XY-Wing、単純連鎖を順に適用する。最難手筋、適用回数、候補削除数を記録し、人間手筋で残った部分だけバックトラック探索する。ratingは手掛かり数、高度手筋、候補削除、未解決数、探索分岐・ノード数を合成する。

### classicの生成手順

1. 基本パターンの行、列、数字をseed付き乱数で並べ替え、正しい完成盤を作る。
2. マスの順序をseed付き乱数でシャッフルし、1マスずつ数字を抜く。
3. 抜くたびにAlgorithm X / Dancing Linksで解を最大2個まで数える。解が1個でなければ数字を戻す。
4. 入門では、さらに裸のシングルだけで最後まで解けることを毎回確認する。
5. 目標手掛かり数まで抜いた候補を分析し、難易度に応じて採用する。

| 難易度 | 目標手掛かり数 | 生成候補数 | 採用条件 |
| --- | ---: | ---: | --- |
| 入門 | 50 | 1 | 一意解かつ裸のシングルだけで完走 |
| やさしい | 42 | 1 | 一意解 |
| ふつう | 34 | 2 | ratingが最大の候補 |
| むずかしい | 28 | 3 | ratingが最大の候補 |
| エキスパート | 24 | 6 | ratingが最大の候補 |

一意性のために数字を戻す場合があるため、手掛かり数は目標より多くなることがある。入門を「空欄が少ないだけ」にせず、候補が1つのマスを順に埋める最初の手筋だけで完走できることを生成契約にした。

### ratingの意味

classic／symmetricのratingは、空欄数、適用した人間手筋と回数、候補削除数、手筋適用後の未解決数、残りを解く探索分岐・ノード数を合成した相対指標である。Killerは与え数字数、ケージ数、ケージサイズ、単独ケージ数から専用ratingを算出する。

入門は100 seedの回帰テストで裸のシングル完走を強制し、classicとKillerはいずれも代表seedの平均ratingが入門からエキスパートまで昇順になることをテストする。ratingは異なる問題タイプ間の絶対比較ではなく、同じタイプ内の相対評価として扱う。

### 旧LEVEL1からLEVEL3との違い

旧版は完成盤からランダムに数字を抜く点では現行版と同じ発想だった。LEVEL1は各マスの候補列挙、LEVEL2は行・列・3 × 3ブロック内で数字を置ける場所が1つだけになる隠れシングル相当、LEVEL3は確定候補を交差する行・列・ブロックへ伝播する処理まで使い、抜いたマスの候補が1つに絞れなければ数字を戻していた。

現行の入門、やさしい、ふつう、むずかしいは旧LEVEL1からLEVEL3の番号を付け替えたものではない。全難易度で厳密に解の個数を数え、手掛かり目標とratingで段階を作る。エキスパートは旧版に対応する実装がなく、6候補から探索複雑度の高い盤面を選ぶ2026年版独自の追加である。

## マインスイーパ

- 最初に開くマスが決まってから地雷を配置し、そのマスと周囲8マスを安全にする。開始直後の敗北を許さない。
- 推測不要モードでは、公開数字、残り地雷数、制約の包含関係から安全マスと地雷を確定するソルバーで候補盤面を最後まで解く。論理だけで完走できる候補だけを採用する。
- 推測不要をOFFにした場合は、初手安全だけを保証するクラシック配置とする。両モードを同じものとして説明しない。
- 共有URLには最初のマスと生成モードも含め、同じseedでも初手が違えば別配置になることを明示する。
- タッチ／ペンは「開く／マーク」を選択でき、マークは旗、`?`、解除の3状態を循環する。右クリックと長押しもマーク操作として残す。ポインターが閾値以上動いたらドラッグとして扱い、開封とマークをキャンセルする。
- ベストスコアとベストタイムは難易度別に保存する。踏んだ地雷と誤った旗は結果画面で区別する。

## 四川省

- 同じ牌2枚を、盤面内の空白または盤外を通り、2回以内の方向転換で結べる場合だけ消す。
- 経路探索の状態は、位置、進行方向、曲がった回数である。幅優先探索で最短の合法経路を求める。
- 配牌は、満杯の盤面から合法的に取り除けるペアを順に記録し、その逆向きに同じ牌を割り当てる。記録順に消せば完走できるため、生成時点で可解性を持つ。
- 難易度は牌数だけでなく、初期合法手数、途中の平均分岐、2回曲がる経路や盤外経路の比率を含むmobility評価で作る。
- 経路アニメーションは判定結果の説明であり、入力を長時間ブロックしない。クリア後も初期盤面を確認できるようにする。

## 入力と画面設計

### 明示的な開始操作

新しいゲームはタイマーと入力を停止したSTART待機状態にする。設定・難易度・問題タイプは開始前でも変更できる。START押下時に実盤面コンテナーへ`scrollIntoView({ block: 'center' })`を実行し、次イベントループからカウントダウンを開始する。非表示タブで停止する`requestAnimationFrame`には依存しない。

### 画面に合わせる倍率

マインスイーパは表示領域と行列数からセルサイズを、四川省は基準盤面寸法と表示領域から倍率を計算する。内側余白と枠線を差し引き、fit後は盤面の`scrollWidth`と`scrollHeight`が表示領域を超えないことを確認する。手動ズームは併存させる。

### Pointer Eventsを共通入口にする

マウス、タッチ、ペンを別々のゲーム処理へ分岐しすぎず、Pointer Eventsから同じ操作関数を呼ぶ。ブラウザー既定動作の抑止は必要な範囲に限定する。

- 数独のペン操作は遅延`click`を待たず、`pointerdown`でセルを先に選択する。選択値はrefにも同期し、直後の数字入力が1つ前のセルへ入る競合を防ぐ。
- 長押しはタイマーだけで確定せず、移動距離、`pointercancel`、スクロール開始で必ず解除する。
- マインスイーパのタッチ／ペンは「開く／マーク」を明示選択できる。マウス左／右クリックとキーボード操作は従来動作を維持し、長押しはマークのショートカットとして残す。
- 「ペン入力を安定化」は現在の入力がペンのときだけゲーム内ボタン上のスクロールを抑止する。指での通常スクロールまで無効にしない。
- 盤面内スクロールが端へ達したらページ全体へ引き継ぐ。ゲーム領域に閉じ込めない。
- キーボード操作、フォーカス表示、`aria-label`を残し、色や音だけを状態伝達手段にしない。

### オーバーレイは盤面より確実に前へ出す

設定、共有、確認、結果の各ダイアログはPortalでアプリ本体の積層コンテキストから分離する。開いたときの初期フォーカス、Tab移動、Escape、閉じた後のフォーカス復帰を確認する。単に大きな`z-index`を設定するだけで解決しない。

### 動きと音は補助にする

Web Audio APIでBGMと効果音を生成し、外部音源へ依存しない。master gainとcompressorを通し、100%で聞き取れる一方、効果音が破綻しない値にする。OSの`prefers-reduced-motion`とアプリ内の追加アニメーション設定を尊重し、動きや音がなくても操作結果を理解できるようにする。

## PWAと公開

- GitHub Pagesの基底URLは`/chikichiki-puzzles/`である。manifestの`id`、`scope`、`start_url`、Viteの`base`、Service Workerの登録範囲を同じサブパスに保つ。
- Workboxの更新は即時強制せず、利用者へ更新を通知する。キャッシュ変更後は、通常再読み込みだけでなく更新適用とオフライン起動を確認する。
- `main`へのpushでGitHub Actionsが`npm ci`、Lint、全テスト、本番ビルドを実行し、成功後にGitHub Pagesへ公開する。
- 公開URLは <https://kenrouse.github.io/chikichiki-puzzles/> である。

## 検証基準

変更後は最低限、次を実行する。

```powershell
npm run lint
npm test
npm run build
```

ゲームエンジン変更時は、同一seedの決定性、一意解または可解性、難易度間の相対関係を対象テストで確認する。入力やレイアウト変更時は、デスクトップとモバイルの実画面に加え、該当するマウス、タッチ、ペン操作を確認する。PWA変更時はGitHub Actionsと公開URLの更新までを完了条件にする。

## 維持する判断

- 見た目を変えるためにエンジンの公平性を弱めない。
- 難易度を手掛かり数や盤面サイズだけで説明しない。
- seed再現、保存データ、共有URLを暗黙に壊さない。
- ペンの問題をタッチやページスクロールの全面禁止で回避しない。
- 旧版の由来は残すが、未実装だった機能や現行の保証を旧版由来として語らない。
- 未検証の端末操作や公開状態を「確認済み」と記録しない。
